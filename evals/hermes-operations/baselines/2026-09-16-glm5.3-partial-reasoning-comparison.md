Code under test: `04bff32`  
Main model: `z-ai/glm-5.3` via OpenRouter

## Tool-name consistency

Both GLM full runs used canonical `mcp__cafe_os__...` tool names without the nonexistent compact aliases seen in the Qwen baseline. The focused green-lot smoke case also passed 3/3 turns at GLM low, and the full low run repeated that pass. On this sample, GLM is materially more reliable at emitting exact tool names.

## Behavioral comparison

GLM low passed the simple clarification, provider, roast, and update flows. It failed every purchase requiring two named foreign-key lookups. In the uncertain voice-note confirmation, it invented an all-zero lot UUID and an unsupported note, then created a new pending proposal instead of executing the confirmed one. Low is therefore not safe enough to become the default despite its speed and tool-name fidelity.

GLM high passed the missing-weight purchase and the four-turn uncertain voice-note flow. It resolved the provider and lot to authoritative IDs, omitted unsupported optional fields, created a pending proposal, and executed the exact proposal after confirmation. It also retained canonical tool names throughout.

The only high failure was the required-only Spanish purchase. The first turn queried the provider correctly, then queried `Chiapas lavado` as another provider instead of as a green-coffee lot. It displayed a prose proposal without storing a pending operation. The confirmation turn performed more reads and asked for confirmation again rather than executing a write.

An isolated high retry reproduced the same resource-type error and failed 0/1 scenario. This is not a transient capacity failure.

## Root-cause inference

The failing trace contains two `query_records` calls emitted in one assistant response. Both calls were formed before the middleware's post-tool hook could advance the ordered lookup state from `provider` to `green_coffee_lot`, so both used `resource: provider`. This is an inference from the trace and should be verified with a focused harness test.

The best next experiment is one of:

1. set `parallel_tool_calls: false` whenever `lookup_resources` contains more than one ordered resource, allowing the middleware to update the phase between calls; or
2. extend `query_records` with a typed batch request that resolves provider and lot in one deterministic envelope.

Do not switch the production default yet. GLM high is the strongest candidate, but the remaining reproducible ordered-lookup failure and approximately nine-times higher benchmark cost should be addressed or explicitly accepted first.
